Security infrastructure case study

Wazuh Stack Bring-Up

Current public scope: a Wazuh Indexer on one Ubuntu 24.04.4 LTS VM and a Wazuh Dashboard on a second VM in VMware Workstation, with TLS, JVM sizing, configuration changes, and verification notes documented in the repo. The manager or server layer, agents, and alert pipeline are not deployed yet.

Repository Indexer guide Dashboard guide
2 VMs Dedicated Ubuntu 24.04.4 LTS machines for indexer and dashboard.
192.168.71.100 Static IP assigned to the Wazuh Indexer on the VMware NAT network.
192.168.71.103 Static IP assigned to the Wazuh Dashboard with browser access over HTTPS.
TLS + tuning Certificate workflow, memory locking, JVM sizing, and service verification are documented.

Current scope

Task
Bring up a Wazuh indexer and dashboard environment and record the deployment work in a public repo.
Environment
A single-node Wazuh Indexer VM plus a separate Wazuh Dashboard VM, both configured on Ubuntu Server 24.04.4 LTS in VMware Workstation.
Artifacts
Public deployment guides, VM sizing, port requirements, TLS generation steps, verification commands, and correction notes in the repo.
Completed
Indexer deployment, dashboard deployment, certificate regeneration, and documented verification of active services and accessible dashboard login.
Not yet implemented
Manager or server layer, agents, alert flow, and a more resilient design than the current single-node indexer setup.

Verification and issues

Certificate regeneration

The dashboard node was missing from the first certificate config, so the certificates were regenerated with the correct hosts.

Service checks

The repo records cluster initialization, service status checks, and dashboard access over HTTPS.

Current limit

Current build stops at indexer plus dashboard; there is no manager or server layer, agent path, or high-availability cluster.

Documented architecture

The diagram reflects the current dashboard and indexer VMs plus the planned additional node referenced in the repo.

Current network: VMware NAT on 192.168.71.0/24. Ports called out in the repo: 443 for the dashboard and 9200 for Dashboard to Indexer communication.

Configuration artifact

This excerpt reflects the values documented in the public deployment guides for the single-node indexer setup and dashboard connection.

# Wazuh Indexer
network.host: 192.168.71.100
node.name: wazuh-indexer
cluster.initial_master_nodes: ["wazuh-indexer"]
bootstrap.memory_lock: true

# JVM sizing
-Xms4g
-Xmx4g

# Wazuh Dashboard
server.host: 192.168.71.103
opensearch.hosts: ["https://wazuh-indexer:9200"]
server.ssl.certificate: /etc/wazuh-dashboard/certs/wazuh-dashboard.pem
server.ssl.key: /etc/wazuh-dashboard/certs/wazuh-dashboard-key.pem

The repo also records the CN mismatch correction in opensearch.yml.

Recorded verification steps

Check What was verified
Cluster init indexer-security-init.sh completed and the log reported Node has been initialized.
Service state systemctl status wazuh-indexer and systemctl start wazuh-dashboard are part of the written verification flow.
Browser access The dashboard guide records access to https://192.168.71.103 and the expected login page.
Expected limitation The dashboard shows a no-server warning because the manager or server layer is not deployed yet.

Current limitations

  • Single-node indexer means no high availability and no resilience if that VM goes down.
  • The manager or server layer is not deployed, so the current setup stops short of a full Wazuh workflow.
  • The dashboard warning about no connected server is expected until the missing layer is added.
  • Public artifacts currently rely on written deployment notes and configuration excerpts rather than screenshots.
